# ADR-0065: The desktop web view is TypeScript built with Vite, over a client generated from the OpenAPI snapshot

- **Status:** Proposed
- **Date:** 2026-10-16

## Context

The local API publishes an OpenAPI schema so that the desktop app's client can be generated from it ([ADR-0061](0061-the-local-api-is-a-fastapi-adapter-over-the-python-api-shipped-as-an-optional-extra.md)), and the schema is committed as a snapshot, `tests/unit/localapi/openapi.json`, that the Python suite holds equal to the served document. The desktop shell's web view ([ADR-0055](0055-the-desktop-shell-is-tauri-2-with-the-engine-as-a-supervised-sidecar.md)) is still a static page, `desktop/ui/`, with no build step: one JavaScript file that calls `GET /v1/status` by hand.

The next stage is the review screen, which calls most of the API: listing, previewing and applying decisions (ADR-0053, ADR-0063), judging (ADR-0059), and unmerge (ADR-0064). Those calls carry versions a client must echo back unchanged, plans told apart by `kind`, and a uniform error envelope (`{code, retryable, message}`) whose codes the [wording brief](../decision-wording.md) maps to messages. Written by hand in untyped JavaScript, every field name is a guess the compiler cannot check, and a change to the API is found only when the screen breaks.

Measured on the snapshot while planning (Node 24.18, pnpm 11.13, TypeScript 5.9.3, openapi-typescript 7.13.0): the generated types are 2,171 lines with no warnings, and an exhaustive `switch (plan.kind)` over the preview's plan union compiles under `--strict`, with `never` in the default branch.

Two constraints shape the build. Tauri embeds the `frontendDist` directory into the shell's binary at compile time and refuses to compile when it is absent (`tauri-codegen`: "this path doesn't exist"), so whatever produces the page must run before `cargo build`. And every file under `frontendDist` is embedded, so it must hold the built page only, never sources or `node_modules`.

## Decision

We make the web view a TypeScript package with one build step.

- **`desktop/` is the pnpm package root** (`package.json`, `pnpm-lock.yaml` committed, `packageManager` pinned). `desktop/client/` is the API client; `desktop/ui/` is the page's source. Vite builds the page into `desktop/dist/`, which is ignored and is Tauri's `frontendDist`.
- **The client's types are generated by openapi-typescript** from the committed snapshot into `desktop/client/schema.d.ts`, which is committed. A check regenerates them in memory and fails when the committed file differs, so the snapshot stays the single source of truth: an API change that regenerates the snapshot must regenerate the client in the same change.
- **The client's runtime is hand-written and has no dependency.** One function sends a request named by a path template and method of the generated `paths`, with its body typed from that operation's request and its answer from its success response; it adds the base URL and bearer token from the shell's `engine_state`, maps the error envelope to typed errors, and keeps the token out of every error and log.
- **A Node CI job** installs with the frozen lockfile, typechecks, runs the client's unit tests, runs the drift check and builds the page. The shell's jobs build the page before compiling.

## Consequences

- Easier: the review screen is written against types the compiler checks; an API change that breaks a field the app uses fails typechecking in CI rather than in the app; plan kinds narrow with a `switch`.
- Easier: the error codes the wording brief names are typed constants, held complete by a test against the engine's error table.
- Harder: the repository gains a second package manager and a Node toolchain. Building or testing the shell, even `cargo test`, now needs the page built first (`pnpm --dir desktop install` and `pnpm --dir desktop build`), and the shell's CI jobs install Node.
- Harder: a change to the API needs `pnpm --dir desktop generate` beside the snapshot regeneration, and the Node job fails until it is run.
- The page is no longer "static files with no build step"; the architecture document changes to say so.
- No npm package ships in the page: every dependency is a development dependency, pinned by the lockfile.
- The client's call function is ours to maintain: path filling, query encoding and the per-operation type lookups, about forty lines with tests.

## Alternatives considered

- **Keep the page as plain JavaScript, typed with JSDoc against the generated `.d.ts` and checked by `tsc --checkJs`.** No build step at all. Rejected: the review screen is the bulk of the app, JSDoc types are verbose and weaker at narrowing, and the build step is a single Vite invocation that vitest already brings in.
- **openapi-fetch**, the runtime of the openapi-typescript project, typing each call from the same `paths`. Measured and rejected: its `Readable`/`Writable` mapped types widen every tuple to an array, and the snapshot has three (`WorkspaceStatus.edges`, `UnmergeVersion.member_digests`, `Applied.merged`), so a type-level test that every method returns exactly the schema's type failed on three methods. A version a screen echoes back would be checked against `string[][]` instead of `[string, string][]`. It would also have been the one runtime dependency in the page.
- **A generator that emits a runtime SDK (Orval, Hey API, openapi-generator).** Rejected: they generate far more code, change their output shape between releases, and openapi-generator needs a JVM. Types-only generation keeps the generated file a pure function of the snapshot.
- **tsc alone, with a copy step for the HTML and CSS.** Avoids Vite but needs a hand-written copy script and cannot import an npm package into a browser page without a bundler or import map. Rejected.
- **Generating the types at build time and not committing them.** Rejected: the generated file is the client's contract with the API and should be reviewable in the diff that changes it.
