# Delta for Desktop Client

## ADDED Requirements

### Requirement: The Client Is Generated From The Committed OpenAPI Snapshot

The desktop app MUST reach the local API through one TypeScript client under
`desktop/client/`, whose types MUST be generated by openapi-typescript from the
committed snapshot `tests/unit/localapi/openapi.json` into
`desktop/client/schema.d.ts`, which is committed. The repository MUST provide one
command that writes the generated file and one that fails, naming the command
that regenerates it, when the committed file differs from what the snapshot
generates. Both MUST use the same generation. The client's operations MUST be
typed from the generated `paths`, each taking and returning exactly the
schema's types (tuples included), so that a field the client or the page uses
and the snapshot no longer has fails typechecking. The error codes the client
names MUST equal the codes the engine's error table defines.

#### Scenario: A snapshot change without a regenerated client fails

- GIVEN the snapshot was regenerated after an API change
- AND `desktop/client/schema.d.ts` was not
- WHEN `pnpm check:schema` runs
- THEN it exits non-zero and names `pnpm --dir desktop generate`

#### Scenario: The committed client matches the snapshot

- GIVEN `desktop/client/schema.d.ts` was generated from the current snapshot
- WHEN `pnpm check:schema` runs
- THEN it exits zero

#### Scenario: An error code the engine adds is missing from the client

- GIVEN `src/openkos/localapi/_errors.py` defines a code the client's list lacks
- WHEN the client's tests run
- THEN the error-code test fails naming that code

#### Scenario: A plan narrows on its kind

- GIVEN a decision preview
- WHEN a caller switches on `plan.kind` over `merge`, `relate`, `set_tier` and `keep_distinct`
- THEN each branch sees that plan's own fields
- AND a default branch typed `never` compiles

### Requirement: The Client Takes Its Address And Token From The Engine State

The client MUST be created from a `ready` engine state, as the shell's
`engine_state` command returns it, and MUST send `Authorization: Bearer <token>`
on every request. It MUST refuse, before sending any request, a base URL whose
scheme and host are not `http://127.0.0.1` or whose path is not `/v1`. The token
MUST NOT appear in any error the client raises (its message, its string form or
its JSON form) nor in the client's own string or JSON form.

#### Scenario: Every request carries the token

- GIVEN a client created from a ready state with token `T` and base URL `http://127.0.0.1:4242/v1`
- WHEN the caller reads the workspace status
- THEN the request is `GET http://127.0.0.1:4242/v1/status`
- AND it carries `Authorization: Bearer T`

#### Scenario: A foreign base URL is refused

- GIVEN a ready state whose base URL is `http://example.com:4242/v1`
- WHEN a client is created from it
- THEN creation fails and no request is sent

#### Scenario: The token never reaches an error

- GIVEN a client created with token `T`
- WHEN a request fails with an error envelope, with a body that is not the envelope, or because the engine cannot be reached
- THEN neither the error's message, nor its string form, nor its JSON form contains `T`
- AND neither the string nor the JSON form of the client contains `T`

### Requirement: The Error Envelope Becomes A Typed Error

A non-2xx response carrying the envelope `{code, retryable, message}` MUST be
raised as an API error with the response's status, the envelope's code,
`retryable` and message, and the `Retry-After` seconds when the header is
present. A non-2xx response without the envelope, or a 2xx response whose body is
not JSON, MUST be raised as a protocol error. A request `fetch` rejects MUST be
raised as an engine-unreachable error. The client MUST tell a busy workspace
(`workspace_busy`) apart as "try again", and MUST offer a retry that repeats a
call only while it fails with `workspace_busy`, waits `Retry-After` seconds
between tries, never waits past a deadline (five seconds unless the caller sets
one), and rethrows the last error when the deadline is reached. It MUST NOT
retry any other failure automatically.

#### Scenario: A busy workspace is a try-again error

- GIVEN the engine answers 503 with `{"code": "workspace_busy", "retryable": true, ...}` and `Retry-After: 2`
- WHEN the caller applies a decision
- THEN the client raises an API error with status 503, code `workspace_busy`, `retryable` true and `retryAfterSeconds` 2
- AND it is classified as busy

#### Scenario: A busy apply is retried until it succeeds

- GIVEN the engine answers `workspace_busy` once and then 200
- WHEN the caller applies a decision through the busy retry
- THEN the client sends the request twice and returns the second answer

#### Scenario: The busy retry stops at its deadline

- GIVEN the engine answers `workspace_busy` every time
- WHEN the caller applies a decision through the busy retry with a deadline
- THEN the client stops before the deadline and raises the last busy error

#### Scenario: Other refusals are not retried

- GIVEN the engine answers 409 `write_drift` (retryable) or 422 `invalid_selection`
- WHEN the caller applies a decision through the busy retry
- THEN the client sends the request once and raises that error

#### Scenario: The named refusals keep their codes

- GIVEN the engine answers `request_too_large`, `invalid_selection`, `merge_group_interrupted`, `unmerge_interrupted`, `survivor_missing`, `not_merged` or `survivor_edited`
- WHEN the client raises the error
- THEN its code is that code, and the last three are classified as unmerge refusals

#### Scenario: A body that is not the envelope is a protocol error

- GIVEN the engine answers 502 with an HTML body
- WHEN the caller reads the status
- THEN the client raises a protocol error carrying the status

### Requirement: CI Holds The Client To The Snapshot

Continuous integration MUST run, on every pull request and push the CI workflow
runs on, a job that installs the desktop package from its committed lockfile
without updating it, typechecks the client and the page, runs the client's unit
tests, runs the snapshot check and builds the page.

#### Scenario: A drifted client fails CI

- GIVEN a change that regenerates the snapshot but not the client
- WHEN CI runs on the pull request
- THEN the desktop client job fails
